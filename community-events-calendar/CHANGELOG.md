Custom WordPress plugin. Not a git repo — this file is the change history in lieu of a commit log. Versions follow semver: PATCH = fixes, MINOR = new backward-compatible features, MAJOR = breaking changes (none yet).

## 1.27.0

**Phone month grid replaces the long phone agenda** (owner request: the phone calendar "goes to a list view and is inconvenient to scroll through"). Below 700px wide, `[cec_calendar]` used to show every day of the month with every event running that day, about 84 entries and roughly 22 phone screens for October 2026, because each national weekend repeats on every day it runs. It now shows a compact month grid on one screen, and tapping a day lists that day's events underneath. The design was approved from a mockup built with the real October 2026 events.
- **Grid** (`CEC_Month_Grid::render_phone()`): day buttons with up to 3 dots for single-day items (`PHONE_MAX_DOTS`), thin bars for multi-day items drawn across the days they run (at most `PHONE_MAX_LANES` = 2 per week row, same greedy lane packing as the desktop grid), and "+N" for the rest. Weekday labels follow the First Day of Week setting. Today is ringed; the selected day is filled.
- **Tapped-day list** (`render_phone_day_list()`, mirrored in `frontend.js` `selectPhoneDate()`/`phoneCard()`): heading, event count, then what **starts that day** and what's **still running** ("day 9 of 12"), so a one-night event isn't buried under a 12-day festival. Each event is one full-width tappable card (title, time or date range, place and price). It opens on today, or on the first day with events when viewing another month. The server renders the initial list, so it shows before JavaScript loads. Tapping a day also updates the desktop click-a-date panel, so the two stay in sync.
- **Additive payload fields** in `.cec-cal-data`: `id`, `endDate` (true end date), `time` (start time with timezone, single-day timed events only) and `status`. Grid items gain `detail['time']`; items from other callers without it fall back to "All day" / the date range.
- **Theme-proofed from the start:** every day button and card is scoped under `.cec-calendar-wrap` with `!important` on its visual properties. Hello Elementor's `reset.css` restyles every `button` (pink 1px border, `#cc3366` text, 8px 16px padding), and without this it repainted the day cells. That was confirmed on a copy of the live page before the fix.
- Removed: the `.cec-cal-agenda` markup and CSS (only used by this view; nothing else in the repository referenced it). Desktop (700px and wider) is unchanged. `tests/snap.php` output will differ in the phone section and the payload, intentionally.
- **Verification:** a test page made from the live colandb.com Community Events page (real theme CSS and real October 2026 events), with the phone section generated by a Python copy of `render_phone()` and the new `frontend.css`/`frontend.js`. At 375px: the desktop grid is hidden and the phone grid shown; day cells keep their own styling against the theme; weekday labels line up with the day columns; dots never overlap bars; no sideways scrolling; tapping Oct 9 lists 4 weekends starting plus Kink 101, then Maspalomas "day 9 of 12"; Oct 20 lists MAsT; an empty day shows the empty note. **Not run in a real WordPress install** (no PHP on this Mac): the PHP was reviewed by hand and bracket-checked, and CI runs `php -l`. Check the live calendar at phone width after updating.

New `when_display` (from `CEC_Event_Helper::format_when()`) keeps the end date: "Fri, Oct 9 – Sun, Oct 11, 2026", or "Fri, Oct 9, 2026 6:00 pm – Sun, Oct 11, 2026 2:00 pm" for an event with real times.

New `display_time_mode()` shows those as dates only, everywhere a time is displayed (event page, cards, list date block, preview), with no timezone label. Display only: the stored times, the saved Time Details setting and all exports are unchanged. Exposed as `data()['display_time_mode']`; forms keep using `time_mode`.
- **Titles reached calendar apps with HTML codes.** WordPress turns a typed " - " into the display code `&#8211;`, and the `.ics` `SUMMARY` used that display version, so "MAsT:Columbus - October Meeting" arrived as "MAsT:Columbus &#8211; October Meeting". New `data()['title_plain']` (the title exactly as entered) and `CEC_Event_Helper::plain_text()` are now used for the `.ics` title and description, the Google Calendar link, schema.org `name`/`description`, and the share links (WhatsApp, Telegram, SMS, X, email). On-page titles are unchanged.

- Verified on staging before release: the date and price-note rules were checked in a Python port against real events from the site; the filter-bar CSS was checked live against the real theme by injecting it into the staging page.

## 1.25.1

**Fix: the per-event timezone (added in 1.22.0) was ignored by everything that sends an event's time off the site** — the downloadable/subscribed `.ics` files, the "Add to Google Calendar" link, and the schema.org `startDate`/`endDate` search-engine data. All three converted the stored wall-clock time using the *site's* timezone (`get_gmt_from_date()` in `CEC_Ical::utc_ics()`, `date_i18n( 'c' )` in `CEC_Event_Helper::event_schema()`), so any event set to a timezone other than the site's landed at the wrong time in subscribers' calendars. Example, found on a real WordPress install with the site set to America/New_York: an event at 6:00–8:00 pm America/Chicago displayed correctly on its own page ("6:00 pm – 8:00 pm CST") but exported as 23:00–01:00 UTC (an hour early) and as `18:00-05:00` in schema.org. The error grows with distance between the two zones.
- New `CEC_Event_Helper::local_datetime( $raw, $timezone )`: turns a stored `_cec_start`/`_cec_end` value into a real `DateTimeImmutable` in the event's resolved timezone (`data()['timezone']` — event, then venue, then site, the same rule the event page already uses). An invalid stored zone falls back to the site timezone rather than fataling. Any future code that emits an absolute time must use this rather than `get_gmt_from_date()` or `date_i18n( 'c' )`.
- `CEC_Ical::utc_ics()` now takes the timezone and converts through `local_datetime()`; both of its callers (ICS `DTSTART`/`DTEND` and `google_calendar_url()`) pass `$data['timezone']`.
- `event_schema()` now emits `startDate`/`endDate` with the event's own UTC offset.
- Not changed: on-page display (already correct — it shows the stored wall-clock time plus the event's own zone abbreviation), all-day events (`VALUE=DATE`, no timezone involved), and the "Past" calculation and list/calendar date queries, which compare wall-clock times against the site's current time and can be off by the zone difference for a few hours around an out-of-zone event's end. That last item is a separate, smaller issue, left for a decision rather than widened into this fix.
- **Verified in a real WordPress 7.1.2 install** (PHP 8.3, SQLite; the same WordPress version as the production site) — the first change in this plugin's history checked this way rather than by the Python/mock-markup methods in `TECHNICAL_BRIEF.md` Appendix B. `php -l` passes on all 39 PHP files. With the site on America/New_York, checked the ICS file, Google Calendar link and schema.org output over HTTP for: an America/Chicago event (now `20261104T000000Z`, `-06:00`); an event with no timezone of its own (falls back to the site zone, unchanged result); an America/Los_Angeles event on a summer daylight-saving date (`PDT`, `-07:00`); an event with a corrupted stored timezone (falls back to the site zone, no error); and an all-day multi-day event (unchanged `VALUE=DATE` output). Zero PHP warnings/notices from the plugin in `debug.log` across all of the plugin's shortcodes, single event pages, both ICS feeds, the RSS feed, and the calendar/filter AJAX endpoints.

## 1.25.0

**Phase 1d — the last of Phase 1: duplicate detection and a real editor preview** ("Give editors duplicate detection, event status controls [already built], and a preview of the list card, detail page, and month view"). This completes Phase 1 of the v2 project brief.

- **Duplicate detection**: a new "Event Preview" box (wp-admin, below Event Details) and a matching section on the front-end Calendar Manager dashboard's edit form flag other events whose title is a close match (PHP's own `similar_text()`, ≥70%) **and** whose start date falls within a day of this one — a conservative heuristic flag for a human to judge, never a hard block, consistent with this project's safe-by-default standard. Deliberately excludes anything in the same recurring series (a weekly class's own occurrences legitimately share a title and land close together — that's an intentional repeat, not an accident).
- **List card preview**: the same box renders this event's real `event-card.php` markup — exactly what it will look like in Grid view — regardless of its current (possibly unpublished) status.
- **Detail page preview**: a "Preview Full Event Page" link using WordPress's own native, nonce-protected preview mechanism (`get_preview_post_link()`) — no new plugin code needed here; `is_singular( 'cec_event' )` and this plugin's own `pre_get_posts` filters were confirmed to already behave correctly for a front-end preview request.
- **Month view preview**: `render_month_html()` gained an optional `$preview_post_id` parameter that splices one specific not-yet-published event into its own real month's results (everything else in that month still has to be genuinely published) — a dashed outline marks it as "not real yet" on both the day pill and a multi-day bar. On the front-end dashboard this is fully interactive (Prev/Next/Today/click-a-date all work, for free — that page already loads `frontend.js` globally); in wp-admin, this version's own `enqueue_admin()` now also loads the public `frontend.css`/`frontend.js` (with their own localized `CEC` object) specifically so the same interactivity works there too, rather than hand-duplicating the calendar's own nav/click-to-select JS a second time into `admin.js`. The one overlap this creates — `admin.js`'s and `frontend.js`'s own separate copies of the admission/location field-toggle handler both now bind in wp-admin — is harmless: both do the identical idempotent toggle, so calling it twice has no different effect than once.
- **Real bug caught before shipping, by checking against a realistic wp-admin backdrop instead of trusting the component in isolation**: the preview box's headings and helper text were genuinely illegible — near-white text with no dark surface under it, sitting directly on wp-admin's own white meta-box background. `.cec-editor-preview` now has its own explicit dark background (reads as an intentional themed preview window, not a rendering glitch), confirmed by re-checking the same reconstructed wp-admin layout afterward.
- A second, smaller fix caught the same way: `.cec-editor-preview` wasn't in the stylesheet's own list of wrapper classes that define its local `--cec-card`/`--cec-radius`/`--cec-muted`/etc. custom properties, so the card/calendar previews nested inside it would have silently lost their own correct card/border colors. Added to that list alongside the plugin's other top-level wrappers.
- **Verified**: a faithful Python port of PHP's own `similar_text()` algorithm was run against realistic title pairs (an exact duplicate, a resubmission with a year appended, a punctuation variant, two genuinely different events with similar names, and two clearly unrelated events) to confirm the 70% threshold catches the real cases without over-flagging; the wp-admin preview box was checked against a reconstructed realistic wp-admin postbox layout (not just viewed in isolation), which is what caught both CSS issues above before shipping rather than after a live report.

**Phase 1 of the v2 brief is now complete** (1a data model, 1b Upcoming-list redesign, 1c Past/first-weekday/URL-filters/agenda, 1d duplicate detection + preview). Phase 2 (member accounts/profiles/My Calendars) and Phase 3 (shared planning/recurring tasks) remain a separate, not-yet-started, confirmed-to-need-its-own-plugin body of work per the brief's own explicit recommendation.

## 1.24.1

- **Verified the bug was real before trusting the fix**: reconstructed the old, unscoped CSS under separate class names, loaded it against a hostile mock theme carrying the exact compound-selector-plus-`!important` pattern described above, and confirmed it reproduced the user's screenshot exactly (dark, illegible buttons) — then confirmed the new scoped rules, loaded from the actual shipped `frontend.css`, render correctly against that same hostile theme.
- **Also changed per direct request**: `[cec_events]`'s own default `view` is now `"list"` (was `"grid"`) — any existing placement that doesn't pass `view="grid"` explicitly will now show the Phase 1b list redesign by default. ## 1.24.0

**Phase 1c: Past label, first-weekday setting, URL-encoded filters, small-screen agenda view.** All four shipped together per the already-agreed Phase 1c scope.

- **"Past" label**: new `CEC_Event_Helper::is_past()` — derived from an event's effective end (end date/time if known, otherwise its start), never a stored status. Shown as a quiet badge on the single event page (the only place a past event is still reachable, per the brief: "a past event remains on its detail URL and is labeled Past").
- The Upcoming list's (`[cec_events]`) past-event exclusion is now **end-date-aware** instead of the old crude "started within the last day" approximation — an event with an explicit end is excluded once that end has passed, not just its start; an event with no end (a Start-time-only event) is excluded once its start has passed, matching `is_past()`'s own fallback exactly so the query and the display-side label can never disagree with each other. Verified consistent against representative sample data (in-progress multi-day, no-end start-only, future, just-ended) in Python before shipping.
- **First Day of Week** (Events > Settings > Calendar Display), defaulting to Sunday, applied identically to the public and (already shared) member month grids. All 7 weekdays are selectable, not just Sun/Monday, since the underlying rotation math is no harder to support generically. Real day names (not hardcoded English strings) are generated from a known-Sunday reference date rotated to the configured start, so this is also now properly locale-aware for the first time.
- **URL-encoded filters**: `[cec_events]`'s event-type/venue/date-range/sort/view state now round-trips through the URL's own query params (`cec_event_type`, `cec_venue`, `cec_date_range`, `cec_sort`, `cec_view`) — copying or bookmarking the page URL reproduces the same result set. The initial server render reads `$_GET` directly (works even before any JS runs); the JS updates the address bar via `history.replaceState` (not `pushState` — a filter tweak doesn't belong in back-button history) after every Filter/Sort/Grid-List action. Defaults are left out of the URL entirely so the plain/unfiltered page keeps a clean link.
- **Small-screen agenda view** (`[cec_calendar]`, below the existing 700px breakpoint): replaces the compressed month grid outright with a chronological, day-by-day list of every date in the month that has an event — each showing its complete date range (never just "today's slice" of a multi-day span) — rather than just shrinking the grid's fonts/cells. Reuses the exact markup/classes the existing click-a-date detail panel already builds in JS, server-rendered this time, so no new visual language was introduced and the panel itself (redundant once the whole month is already listed) is hidden at the same breakpoint.
- **Verified**: the first-weekday offset math (`lead_blanks`) and the locale-aware header rotation were ported to Python and checked for every one of the 7 possible settings against a real month; the `is_past()`/not-past-query consistency was checked the same way. The weekday-rotated grid and the small-screen agenda were both rendered against the real production CSS in a reconstructed browser harness at desktop and mobile widths and matched expectations exactly.

**Fix:** the 1.14.0 page auto-creation ran multiple times on one real site, producing 5 duplicate copies each of several pages (confirmed live — a wp-admin Pages screenshot showing 5× "Calendar Admin" and 5× "Create an Account"). ## Known scope boundaries / things a future developer should know

- **Not a git repo.** No commit history — this file is the only change record. Consider initializing git if ongoing development continues.
- **RSVP** (`wp_cec_rsvps`), **subscribers** (`wp_cec_subscribers`), and **volunteer inquiries** (`wp_cec_volunteer_inquiries`) are custom tables, created via `dbDelta()`. Table creation runs on `register_activation_hook` **and** is gated behind a `cec_db_version` option checked on `init` (`CEC_Plugin::maybe_upgrade()`), since re-uploading plugin files without deactivating doesn't re-fire the activation hook.
- **Occurrences are real posts.** Any `WP_Query` against `cec_event` that doesn't explicitly want individual recurring dates should exclude them via `meta_query` on `_cec_recurrence_parent_id` (see `CEC_Recurrence::exclude_occurrences_from_admin_list()` for the pattern).
- **Guest/token auth is bearer-token, not session-based** — anyone with the emailed link can act as that submitter for 7 days. Acceptable for this use case (low-stakes, self-service, always re-requestable) but worth knowing if requirements change.
- **All `!important` usage in frontend.css is deliberate**, not accidental bloat — it exists specifically to survive conflicts with whatever active theme/page-builder styling the plugin is dropped into. Don't remove it without re-testing button visibility against the live theme.
- **Color/design tokens** are CSS custom properties (`--cec-primary`, `--cec-secondary`, etc.) set inline from Events > Settings — don't hardcode hex values in new CSS; reference the variables.
